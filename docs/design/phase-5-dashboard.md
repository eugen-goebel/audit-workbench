# Phase 5: Dashboard and live demo

Design spec for the second part of phase 5. Code and tests are built against
this document. If code and spec disagree, the spec is fixed first.

Status: approved 2026-11-02, all recommendations of section 10 taken (E1-E6).
The API and Docker are not part of this spec (section 9).

## 0. Why

`awb run` prints a table, `awb explain` shows one finding and `awb workpaper`
writes a document. None of them answers what a reviewer asks in a meeting: how
do the findings distribute across the modules, which rule fires most often,
where does a segregation-of-duties path actually run, does the ledger follow
Benford, and what crosses module boundaries. A dashboard answers that on one
screen. The live demo makes the project inspectable without installing
anything: a visitor opens a URL and sees the same numbers the tests check.

Two facts decide the design. A run on seed 7 produces 131 findings (A 55,
B 42, C 26, X 8), all 27 registered rules fire, 7 CRITICAL, 73 HIGH,
41 MEDIUM, 10 LOW. And the whole run is cheap: generating the bank takes
1.35 s, loading the evidence and running all rules 1.82 s, peak memory 395 MB.
The dashboard therefore computes everything live. No database, no precomputed
JSON, nothing to keep in sync.

## 1. Who looks at it, and what each one needs

1. **Reviewer** (does not know the tool): where do we stand, what is severe,
   what does this rule test, where does the number come from. Needs counts,
   the rule title in plain words and the evidence hash behind every finding.
2. **Auditor** (uses the tool): one entity end to end. The access path behind
   an SoD conflict, the lines of a suspicious journal entry, the ticket behind
   a deployment. Needs the drill-down and the raw rows.
3. **Demo visitor** (recruiter, auditor from another bank): 60 seconds, no
   install. Needs an honest banner that the data is synthetic and a link to
   the code that generated it.

## 2. How it starts

```
awb dashboard [DATA_DIR] [--seed N] [--port 8501] [--host 127.0.0.1]
              [--no-browser] [--as-of DATE] [--module a|b|c|x|all]
```

- With `DATA_DIR`: the app reads that folder, same loader and same rules as
  `awb run`.
- Without `DATA_DIR`: the app generates the bank for `--seed` (default 7) in a
  temporary directory and runs it. That is the mode the live demo uses.
- `--as-of` and `--module` mean the same as in `awb run`.
- The command starts Streamlit as a subprocess and prints the URL. It does not
  open a browser when `--no-browser` is set (needed in CI and on the server).

## 3. Views

One app, five pages, navigation in the sidebar. Every page starts from the same
`Run` object and the same numbers as `awb run`; nothing is recomputed
differently.

1. **Overview.** KPI row (findings, CRITICAL, rules that fired / rules that
   ran, entities affected). Findings per module and severity as a stacked bar.
   A table of the top rules: id, title, module, count, severity mix. Data basis
   with one row per input file: name, rows, columns, SHA-256 prefix. Banner
   "synthetic data, seed N, generated by `audit_workbench.synth`".
2. **Module drill-down** (A, B, C, X). Filter by severity and rule, table of
   findings sorted most severe first. Selecting one opens the detail: rule
   title and what it tests, entity, description, parameters, regulation
   references with their quote, evidence files with hashes, and the
   rule-specific short form that `reporting.render_details` already produces
   (the SoD access path, the journal entry lines, the change ticket). The raw
   rows of the evidence file are shown for the keys the finding names.
3. **Role graph.** The role hierarchy as a directed graph (`AccessData.role_graph`,
   22 roles and 17 entitlements, 39 nodes and 29 edges on seed 7). Nodes are
   roles and entitlements. Selecting an A-05 finding highlights the two paths
   that make the conflict and the accounts that hold them. Selecting a role
   lists the accounts holding it and everything it grants transitively
   (`roles_within`).
4. **Benford.** First-digit and first-two-digit distribution against the
   expected curve, per group (employee for B-01, account for B-02), from
   `benford_groups` (33 employee groups and 72 account groups on seed 7, 4 ms
   each). Each chart shows the group's deviation and the threshold; when a
   group is also a finding, the chart links to it. Groups below the sample
   size the rule requires are marked as not testable, not as clean: B-01
   judges only groups with at least 1,000 manual line amounts, B-02 only
   groups with at least 5,000.
5. **Cross-module.** The X findings as chains. X-01: the SoD conflict and the
   journal entries posted through it. X-02: the action, the account and the
   function it did not hold. X-03: the exit date and the activity after it.
   Each chain shows the linking key and links into the matching module pages.

When `ground_truth.json` is present, the overview also shows the evidence
quality: injected issues matched N/N and findings without a ground-truth
counterpart M. That is the same comparison `awb check-ground-truth` runs, moved
into `reporting.py` so the CLI and the dashboard cannot drift apart.

## 4. Data flow and cost

- One `load_run` call per session, cached by `(data directory, as-of, module,
  seed)` with `st.cache_data`. Switching seed generates and runs again (about
  3.2 s) instead of restarting the app.
- The views layer never imports Streamlit. It takes a `Run` and returns plain
  data: dataclasses and pandas frames. `dashboard/app.py` only renders them.
  That keeps the logic testable without a browser.
- Nothing is written to disk. A download button offers the findings as CSV and
  as the markdown table `awb run --format markdown` prints, generated in
  memory.
- Peak memory measured: 395 MB for generate plus run. The free tier of
  Streamlit Community Cloud has a memory limit (about 1 GB in practice), so one
  cached run fits with room for the session state. Two seeds cached at once
  would be tight, so the cache holds one entry. The deployment is measured, not
  assumed.

## 5. Honesty and reproducibility

- The banner names the generator, the seed and the repository. The demo never
  suggests real client data.
- The seed comes from the URL (`?seed=11`), so a reader can reproduce what they
  see with `awb generate --seed 11`. A seed without a generated bank on the
  server is generated on the fly; unknown or invalid seeds are rejected.
- Every finding shows its evidence file and the hash prefix; the overview shows
  the full hashes. The same numbers are what the CI ground-truth job checks on
  seeds 7 and 11.
- The app is read-only. No uploads, no login, no persistence.

## 6. Dependencies and deployment

- Optional extra `dashboard`: `streamlit` and `plotly`, next to the existing
  `workpaper` extra. Core stays lean; CI installs all extras and runs the app
  tests.
- `dashboard/requirements.txt` with the pinned versions of those two libraries,
  for the cloud build. Streamlit Community Cloud installs the first dependency
  file it finds and prefers the entrypoint's directory over the repository
  root; without this file it would pick the repository's `uv.lock`, which does
  not carry the optional extras. The deployment is verified during the build
  step, not assumed: open the URL, check the numbers against seed 7, check that
  the package imports.
- Streamlit Community Cloud, public repository, branch `main`, main file
  `dashboard/app.py`. Free tier: about 1 GB memory, the app sleeps after
  inactivity and wakes on the first visit.
- The README gets a screenshot from a real run (never from made-up data), the
  demo link and the three commands that reproduce it locally.

## 7. Tests

- **Views layer** (`audit_workbench/dashboard/views.py`, no Streamlit import):
  pytest against one generated seed 7 run, built once per session. Overview
  counts equal `awb run`; the severity and module breakdown sums to the total;
  the top-rules table lists a rule with zero findings as zero; drill-down
  filters return the same set as filtering the findings list; the ground-truth
  comparison gives the same recall and precision as `awb check-ground-truth`;
  the Benford view marks groups below the sample size as not testable.
- **App smoke tests** with `streamlit.testing.v1.AppTest`: the app starts
  without an exception, shows the banner, shows 131 findings for seed 7 and
  renders each of the five pages.
- **A guard test** that `views.py` imports neither Streamlit nor plotly, so the
  logic stays runnable in a plain Python session.
- **CI**: a new job `dashboard` runs these tests with all extras installed. It
  stays out of the required checks until the deployment is verified, so a
  flaky browser-less run cannot block merges on its own.

## 8. Build steps (one PR, branch `feat/dashboard`)

1. Move the ground-truth set comparison from `cli.py` into `reporting.py`; the
   CLI calls it. Existing CLI tests must pass unchanged.
2. `audit_workbench/dashboard/views.py` with the five view models and tests.
3. `dashboard/app.py` and `dashboard/requirements.txt`; `AppTest` smoke tests.
4. `awb dashboard` in the CLI, with tests for argument parsing and for the
   subprocess call (mocked, no server started).
5. Extra `dashboard` in `pyproject.toml`, CI job, README section with
   screenshot and demo link.
6. Deploy to Streamlit Community Cloud and verify the URL by hand; record the
   check in section 11.

## 9. Deliberately not in this spec

- FastAPI and Docker: kept for later (decision E3 of the workpaper spec).
- Login, users, saved views, persistence: a read-only demo does not need them.
- German interface: the repository is English throughout.
- Real client data: never, in any view or screenshot.

## 10. Decisions (Eugen, 2026-11-02: every recommendation below accepted)

- **E1 Framework.** Streamlit as planned. Alternatives: Gradio (simpler forms,
  weaker layout), Dash (more control, more code). Recommendation: Streamlit,
  because the plan already names it and the cloud hosting is free.
- **E2 Demo data.** Generate seed 7 at startup (about 3.2 s cold start, no
  repository bloat, one code path) instead of committing 13 MB of CSVs.
  Recommendation: generate. Committed data would also freeze numbers that
  change whenever a rule changes.
- **E3 Dependencies.** Optional extra `dashboard` plus
  `dashboard/requirements.txt`. Alternative: put Streamlit in the normal
  dependencies. Recommendation: the extra, because the core stays installable
  without a web framework.
- **E4 CLI command.** `awb dashboard DATA_DIR` as a thin wrapper around
  `streamlit run`, or only document `streamlit run dashboard/app.py`.
  Recommendation: the wrapper, so the README shows one command and `--seed`
  works without the cloud.
- **E5 Downloads.** Findings as CSV and markdown in memory. Recommendation:
  yes, both, since they cost no persistence.
- **E6 Screenshots.** One screenshot per view in the README (five images) or a
  single overview screenshot with a link. Recommendation: overview plus the
  role graph, the other three as text links.
